# SERP再比較・公開前チェック・ファクトチェック・納品基準

このファイルは以下を定める。

* 工程6：SERP再比較、公開前チェック、最終ファクトチェック、文字数計測
* 工程7：最終納品

CTA・スクリプト・ファイル出力は07、HTML仕様は02、具体性は09に従う。口コミ・評判記事は08の公開前チェックも必須とする。

目的は、

**現在公開しても読者が誤った判断をしない状態まで記事を確認し、条件を満たした最終版だけを完成として納品すること**

である。

点数による自己採点は行わない。形式・数・位置は`scripts/check_article.py`で機械的に確認し、AIは判断が必要な項目（#10）に集中する。

---

# 1. 実行順序

1. 作業ファイル（リサーチDB・構成）を読み直し、完成記事をSERP上位と再比較する（#2）
2. 変化しやすい重要情報を再確認し、ファクトチェック・記事内矛盾・比較と案件訴求を確認する（#3〜#8）
3. 最終GutenbergブロックHTMLを記事本文ファイル `{スラッグ}.md` に保存する（07 #6）
4. `scripts/check_article.py` を実行し、`errors` が0件になるまで修正と再実行を繰り返す。`warnings` と具体性の検出箇所は1件ずつ見直す（#12）
5. 文字数未達なら有用情報を追加して再実行する（#13）
6. 公開前チェックリスト（#10）を確認する
7. 公開前作業を整理し、納品メモを作成して出力する（#17〜#20）

---

# 2. SERP再比較

完成記事をSERP上位SEO競合と再比較する。

* 最優先ニーズ3つを満たしているか
* SERP必須コンテンツを落としていないか
* 競合が答える重要疑問が自記事だけ欠けていないか
* 検索意図ギャップを補えているか
* 読者が最終判断・行動できるか
* 指定案件によって回答範囲を狭めていないか（通常記事）
* 不要な情報量で読みにくくなっていないか
* SERP上位記事の共通内容をまとめ直しただけの記事になっていないか
* 工程1で採用した独自切り口を実際に回答できているか
* その独自切り口によって読者の比較・判断・失敗回避が改善しているか
* 独自性を優先した結果、検索意図や事実正確性を損なっていないか

競合見出しの網羅は目的にしない。重大な不足があれば記事を修正する。

リサーチDBの「競合の回答比較表」と、構成の「採用する提供価値」の対応表を使い、次の二問へ具体的に答える。

1. **このページで、読者が具体的に下せる判断は何か。**
2. **競合と比べて、その判断をしやすくした箇所はどこか。**

回答には本文の見出し・表などの該当箇所と、比較対象の競合URL・該当箇所を付ける。計画書ではなく完成本文で判定し、根拠・条件・比較結果まで実装されているか確認する。

独自切り口を採用していない場合は、無理に優位性を作らず、差別化余地を確認できなかった範囲と、実施した正確性・具体性・使いやすさの改善を記録する。その結果自体は未完成理由にしない。

リライトでも料金・キャンペーンの更新だけで終えず、現在の競合との回答の差を再確認し、リサーチDB・提供価値・本文を更新する。順位下落はAI由来と即断せず、GSC等がある場合は期間・ページ・クエリ群と上昇した競合・SERP形式を確認して仮説を分ける。未提供データを取得済みとして扱わない。

# 3. 納品直前に再確認する情報

特に変化しやすい以下を、工程1で確認済みでも納品直前に再確認する。

* 価格・料金・買取価格
* キャンペーン・クーポン・ポイント・還元額・特典
* 開催期間・終了日
* 対象者・適用条件・対象外
* 手数料
* 在庫
* 対応エリア
* ランキング・比較順位

この再確認が完了した日を、**記事冒頭の「情報最終確認日」**とする。現在日付や記事生成日を機械的に入れない。

---

# 4. 時間依存表現

記事内に以下がある場合は特に確認する。

```text
現在 / 最新 / 今 / 今なら / 開催中 / 実施中 / 終了 / 期間限定 / 今だけ
最安 / 最高額 / 一番お得 / No.1 / 1位 / 最も高い / 最も安い
```

確認できない場合は、削除・再検索・表現調整のいずれかを行う。

「YYYY年M月D日現在」「記事執筆時点」等の情報鮮度を示すだけの日付表現は、冒頭の「情報最終確認日」へ集約する。キャンペーン終了日・発売日・申込期限・制度改定日等の事実固有の日付は削除しない。

---

# 5. 最終ファクトチェック対象

記事内の以下をリサーチDB・一次情報と照合する。

* 数値：価格、金額、割引額、買取価格、相場、ポイント、還元額、手数料、合計額、割合、日数・回数
* 日付：開始日、終了日、締切、発売日、キャンペーン期間
* 条件：適用条件、対象者、対象外、地域、対象商品、契約・解約・キャンセル条件
* 固有名詞：企業名、サービス名、商品名、ブランド名、プラン名、キャンペーン名
* URL：公式URL、SNS URL、口コミ出典URL、その他記事内リンク

---

# 6. 記事内矛盾

導入文、「この記事を読んでわかること」、AIO、本文、表、吹き出し、CTA、FAQ、まとめを相互に照合する。

同じ論点について異なる結論が残っている場合は、古い記述そのものを修正する。訂正文だけ追加して古い記述を残さない。

---

# 7. 比較・案件訴求の確認

指定案件がある場合は以下を確認する。

* 検索意図から自然につながっている
* 案件を選ぶ理由が具体的に伝わる
* ランキング・優位表現に根拠がある

通常記事では、さらに以下を確認する。

* 案件に不利な重要条件を隠していない
* 有力な競合を不自然に除外していない
* 比較軸が読者基準になっている

口コミ・評判記事は08の方針（肯定的な口コミ中心、選ぶ理由が主役）に従って確認する。

---

# 8. CTAの内容確認

位置・数・リンク属性は`check_article.py`で確認される。AIは内容を確認する。案件なしの記事では「対象外（案件なし）」と記録する。

* 本文と事実が一致し、現在有効な情報を使用している
* 未確認の数字、根拠のない希少性・No.1表現がない
* 条件・対象外を誤認させない
* ボタン文言とリンク先の目的が一致している
* リンクが07 #5の順（受領リンク → 確認済みの公式サイトURL → AFF_LINK）で、公式サイトURLは実際に開いて確認した

---

# 9. 冒頭5項目・まとめの内容

項目数は`check_article.py`で確認される。AIは内容を確認する。

* 「この記事を読んでわかること」：具体的な結論、本文と一致、本文にない新事実なし
* まとめ：具体的な結論、本文で説明済み、言い換えによる水増しなし、新事実なし、冒頭5項目のコピーでない

---

# 11. チェック後に本文を変更した場合

ファクトチェックや文字数調整で重要な本文変更を行った場合は、変更箇所に関係するチェック項目を再確認し、文字数を再計測する。古いチェック結果・計測結果を最終判定に使用しない。

---

# 12. 機械チェックと文字数の計測

文字数はモデル自身で数えない。記事本文ファイルに対して以下を実行する（詳細は07 #4）。

```bash
python3 scripts/check_article.py {スラッグ}.md --target-min （記事制作target_min） --target-max （競合由来target_max）
```

* 記事制作target_min＝競合由来target_min（01 #26）、target_max＝競合由来target_max
* 案件なしの記事は `--no-case` を付ける
* 返却された `character_count`、`achievement_rate`、`status` をそのまま記録し、再計算・補正しない
* チェックした版と納品する版を必ず一致させる（本文を変えたら再実行する）

---

# 13. 文字数判定

## クリア

`character_count >= 記事制作target_min` なら文字数条件クリア。

## 未達

`character_count < 記事制作target_min` の場合は完成扱いせず、少なくとも1回以下を行う。

1. 現在の記事とリサーチDBを確認する
2. 検索意図内でまだ具体化・深掘りできる論点を特定する（まず具体性の検出箇所と、再検索リストで回答が薄い項目を確認し、01 #14-1・09に従って具体情報を展開する）
3. Web検索・ブラウザで追加リサーチする（公式一次情報を優先）
4. 新しい有用情報を既存H2/H3へ追加する
5. 必要な場合のみ構成を最小限修正する
6. ファクトチェックする
7. 公開前チェックリストを再確認する
8. `check_article.py`で再実行する

追加できる有用な情報が実質的に尽き、これ以上の加筆が水増しになる場合は、無限に再試行しない。**未完成（文字数未達）**として、不足文字数・追加候補を納品メモの冒頭に明記したうえで2ファイルを出力する。「完成しました」とは報告しない。完成基準は引き下げない。

## 水増し禁止

以下による文字数調整は禁止する。

* 一般論
* 同じ内容の言い換え
* 不要なFAQ
* 不要な会社紹介
* 検索意図外の情報
* 根拠のない具体例
* 既存内容の冗長化

## over_target

`status = over_target`でも、有用な情報であれば長さだけを理由に削除しない。重複・一般論・意図外情報が原因なら整理する。

# 14. スクリプトのエラー

実行エラー時は1回再実行する（ファイルパス・引数を確認する）。

再実行しても計測不能の場合は、**実測本文文字数を確認できないため納品停止**とし、エラー内容をユーザーへ報告する。文字数を推測して納品しない。

`check_article.py` のエラー0件と、02 #29の目視確認で行う。

# 16. PR表記

記事本文へPR表記は追加しない。WordPress側の共通設定を使用するため、公開前作業として共通PR表記が有効か確認する。

# 17. 公開前作業

納品時に必要なものだけ提示する。該当しないものは「該当なし」とする。

* CTAリンク（公式サイトURL・AFF_LINK）のアフィリエイトリンクへの差し替え
* balloonID確認
* 指定画像挿入
* 必要なSNS URL追加
* 公開前作業コメントの削除・差し替え
* 最新価格・条件・キャンペーン再確認
* 比較順位再確認
* CTAと現在条件の一致確認
* WordPress共通PR表記確認
* スマホ・PC表示確認
* 情報最終確認日と実際の再確認日の一致確認

---

# 18. 最も早く古くなる情報・リライト時期

記事内で最も更新確認が必要になりやすい情報（期限付きキャンペーン、クーポン、価格、ポイント還元、在庫、ランキング等）を具体的に特定する。

リライト時期はその情報を基準に、期限が明確なら「終了前」「終了直後」「改定予定日の直後」など具体的に、変動型なら変わりやすさに応じて設定する。

# 19. 工程7：最終納品

07の出力ルールに従い、以下の2ファイルを出力する。

1. 記事本文ファイル `{スラッグ}.md`：最終GutenbergブロックHTML全文のみ（07 #6）
2. 納品メモファイル `{スラッグ}_納品メモ.md`：#20の内容

あわせて作業ファイル `{KW}_リサーチDB.md` も参考として提示する。

記事本文は省略せず全文を保存する。「以下省略」「同様の形式で続きます」等は禁止する。

チャットには記事本文HTMLを貼り付けず、07の「チャットでの報告」に従って要点とダウンロードリンクだけを示す。

完成と報告できるのは、以下をすべて満たす場合だけである。

* `check_article.py` の `errors` が0件
* 公開前チェックリスト（#10）をすべて通過
* 重大問題なし
* 公開前作業整理済み

# 20. 納品メモに記載する情報

## 使用スキル（納品メモの先頭に記載）

* スキル名とバージョン（SKILL.mdの「バージョン」の値をそのまま書く。例：`使用スキル：yamaken-seo-contents-member v2.2.0`）
* 作成日

## 完成判定

* 完成 / 未完成
* 未完成の場合は理由（文字数未達・口コミ不足・確認不能な事実等）と次に必要な作業

## 記事基本情報

* タイトル5案・推奨タイトル・推奨理由
* スラッグ
* メタディスクリプション

## 検索意図・SEO

* SERPの取得元（ブラウザでのGoogle確認 / ラッコキーワード / Web検索）と確認日時
* 最優先ニーズ3つ
* SERP記事方針
* SEO競合分析要約（上位記事の共通回答、主な比較軸、競合の不足、自記事で補った点）
* SERP必須コンテンツ
* 競合が満たしていない検索意図
* 採用した独自切り口・採用理由・改善した読者判断
* 採用する提供価値（A：同じ論点の改善／B：異なる角度の検討結果と採否の要約。詳細はリサーチDBを参照）
* 読者が具体的に下せる判断と、競合より判断しやすくした本文箇所・競合URLと該当箇所（#2の二問）。優位性を確認できなければ、その結果と実施した改善
* 残る未確認事項・比較の限界。多様性枠を採用した場合は根拠と仮説の区別
* 指定案件の位置付け（どんな読者に向くか、どの価値で提案したか）
* 案件訴求方針

## 競合文字数

* 競合文字数の取得元（ラッコキーワード見出し抽出 / 添付資料）
* 各URL全文と文字数 / 計測不能
* success本数・failed本数
* average_count
* target_110
* 競合由来target_min
* 競合由来target_max
* 競合平均の信頼性（reliability）

## 完成記事文字数

* character_count
* 記事制作target_min
* target_max
* achievement_rate
* status

## 具体性・検索行動の完了（09）

# 21. WordPress操作

WordPressへの保存・下書き更新・公開・公開予約は行わない。

**記事本文ファイルと納品メモファイルを出力し、ダウンロードリンクを提示した時点で納品完了**とする。

# 22. 納品停止条件

以下の場合は、解消できなければ最終納品しない（状況と理由をユーザーへ報告する）。

* `check_article.py`が再試行後も実行不能
* 重大な事実誤認を確認でき、解消できない
* 根拠のない重要比較・順位を解消できない
* Gutenberg HTMLの重大な構造エラーを解消できない
* AIだけでは取得不能な重要情報がなければ記事の正確性を担保できない

文字数未達・口コミ不足は納品停止条件ではない。#13・08に従い、追加調査のうえで未完成として明記して出力する。

---

# 23. 最終原則

納品判断では、

**「この記事を現在公開し、検索ユーザーが内容を信じて行動しても問題ないか」**

を最優先する。

文章完成・文字数達成のどれか一つだけでは完成としない。検索意図・事実・文字数・HTML・公開前作業をすべて確認した最終版だけを完成として報告する。
